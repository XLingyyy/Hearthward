# CT-001｜世界状态与库存变更

状态：DRAFT / APPROVAL_REQUIRED；版本候选：0.1。Owner、审批PR：未分配。
来源：GDD v0.3第5、7、10、11、13章；Q215、Q226、Q252—254。

## 目的与非目标

让营地、UI和伙伴使用同一份真实库存。契约不引入用户已否定的库存预留、资源计划锁料或工作优先级；
它只要求一次实际扣除／转移不能重复结算、负数库存或凭空生物资。
不在本契约里定义R03的一次性生产资源、不完整配置物品重量表。

## 候选身份与输入

- `item_id`：稳定类型ID；显示名称可变而身份不变。
- `container_id`：玩家背包、弟弟背包、共享营地仓储等。
- `entity_id`：可持久化世界实例；不以运行时内存地址或显示名称代替。
- `operation_id`、`timeline_epoch`：区分一次执行和当前加载时间线。
- 数量为明确非负整数；重量有单位与精度约定。零重量关键物品不是可以随意删除的普通物品。
- 操作：查询、实际增加、实际扣除、容器转移。公共口粮转换需独立领域规则。

## 候选结果

`SUCCESS`、`INVALID_ARGUMENT`、`UNKNOWN_ITEM`、`INSUFFICIENT_ITEMS`、`CAPACITY_EXCEEDED`、
`STALE_TIMELINE`。返回实际变更数量、相关容器的最新状态或修订，以及可显示的失败原因。
数量不足默认不偷偷当成成功；允许部分转移时必须在调用中明确声明并返回实际数量。

转移必须要么完整产生对应两端结果，要么失败后保持一致；这不是提前预占物资。
是否采用任何具体锁或事务实现由技术负责人决定，产品层仍是“真实用掉时结算”。

## 事件与保存

库存改变事件只在实际成功后发出，包含操作身份与实际delta；不能在开始计划时发“已完成”。
世界与知识消费者按事件更新；重放、重试和读档不得重复增加产物。
共享营地仓库只有一个容器身份，两个访问点不是两份复制库存。

## 必须验证

同一份十件物资转移后原端减少十件、目标增加十件；超负重不改变库存；
两次相同操作不会重复奖励；读回旧档后拒绝旧epoch操作；UI值与实际容器一致。
全部测试使用批准的夹具，最终物品表缺失不由工程Agent随意填。

## 尚需批准

代码公开声明、结果类型、精度／取整、部分转移策略、操作去重保留范围。
消费者：Inventory、Camp、Companion、UI、Save。改变以上语义须通知全部消费者。
