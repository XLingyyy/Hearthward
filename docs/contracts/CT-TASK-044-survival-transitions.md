## 请求与返回候选

命令类别：UseMedicine、CancelAction、BeginRescue、GiveUp、AdvanceSurvival、ApplyDamage、RestoreSnapshot。请求复用campaign、timeline_epoch、operation_id以及动作／实体稳定ID；读取权威当前状态，不能相信UI传来的药量、距离或安全标志。

返回：Accepted／Rejected／Interrupted／Completed／Failed，实际消耗、实际生命变化、失败原因和当前状态版本。常见原因：NO_MEDICINE、RARE_PERMISSION_REQUIRED、DOWNED、OUT_OF_REACH、BLOCKED_PATH、DAMAGED、TARGET_DEAD、DEADLINE_EXPIRED、STALE_TIMELINE、RULE_UNRESOLVED。

- 重复operation_id返回既有收据，不二次扣药、回血或扶起；同一个damage_event_id不能先使人倒地又作为新的残伤致死。
- 命令携带旧epoch直接拒绝。一次失败的路径查询不能谎报救援成功；世界恢复、目标死亡、取消、替换委托都使旧完成回调失效。
- 动作时长、恢复时钟和零饱食扣血时钟依据获批设计表，缺配置返回RULE_UNRESOLVED。不得用Demo即时药品或052纯时钟运算代替生存事件消费。

## 提交与取消边界

用药开始仅锁定可用药量；完成重新核验目标状态、权限和物资，原子提交扣药与效果。受伤中断时，损耗和动作中断在同一提交中完成；非受伤中断释放预留。按已批准D2，完整药有两半份，半份保留实际药量、重量和效力；不可退回并未持有的制作材料。该表示需与后续物品实例、堆叠、转移及存档共同评审。

锁定不改变总库存，但不可再次用于并发制作、交易、丢弃、转移或另一用药动作。事务内拒绝保存／恢复与重入世界提交；事件发布在提交后。技术失败无部分扣药，实际中断损失不当作技术失败退还。

救援不预扣药物，开始和完成都校验存活救援者、待救目标、剩余期限、距离、路径与环境；期间中断清零动作进度，不延长目标倒地due。目标或救援者终态优先，5秒回调不能复活已死角色。

## 统一时间与事件顺序

普通模拟A/W共同前进，跳时只前进W。生存消费者先计算饱食归零、到10%生命、严重饥饿due等最近事件，与043生产／刷新共用事件时间。到due则停止剩余跳时，不先跳到终点再补死因；没有消费链时拒绝跳时。

同时间优先顺序由设计D6裁定：连续量截至边界→到期期限／伤害→生死派生→有效动作完成→旅行→安全保存。对同一角色的多个伤害须先按事件ID去重再按确定顺序处理，不能依赖TMap遍历或网络回调先后。暂停所有对应计时；读档直接恢复，不重放从零到保存时刻的事件。

## 快照最小内容候选

| 内容 | 保存原则 |
|---|---|
| 生命状态 | Alive/Downed/Dead主状态、当前／最大生命、耐力／饱食；保存合法性仍按安全规则，普通新档不得包含Downed／Dead |
| 饥饿 | 严重标志、进入W和due；解除至10的真实结果；不得读档重新发三日 |
| 短计时 | 用药／扶起进度、恢复延迟、持续药剩余A、已提交效力及当前动作ID；锁定物资由同档库存重建 |
| 环境 | 溺水状态和剩余A、已生效持续伤害及其下一事件；不在水下加载时凭空发新10秒窗口 |
| 身份／权限 | 稀有物授权、动作结算收据、当前伤害去重边界；旧时间线结果不能进入新档 |

存档格式升级须在实现任务中另列明确schema及旧档判定。旧Demo没有严重饥饿期限／倒地状态，不能仅凭Hunger=0推算过去何时进入，也不能将Health=0猜成合法Alive。建议旧安全档保留数值并执行经批准的缺失状态迁移；不能迁移的档给出原因并保留原文件。本设计单不更改格式、不指定虚假的历史时间。

## 044实施协调记录（2026-09-26）

- 玩家现有Gameplay生命／饱食／耐力字段保持权威；共享Survival组件引用它们，弟弟由同一组件持有数值，避免双写玩家属性。
- 半份药使用同源物品的显式半份ID，沿用整数堆叠、物品目录与重量计算；不添加新配方。库存组件预留一个物品，所有扣除／交换／转移入口尊重预留，受伤交换为半份，半份再次受伤耗尽。
- 生存动作使用A时间与当前时间线；动作结算之前先检查生命和期限。伤害事件ID去重；恢复切换时间线并清除旧动作引用。
- 保存增加版本化的生存快照。旧档无历史期限：保留可迁移的正生命数值，在保存时刻首次建立必要饥饿状态；零生命旧快照拒绝迁移并保留文件。使用显式版本判定，避免缺失字段采用新类默认值。
- 使用现有Actor伤害、移动和导航API；不引入GAS。参考Epic的[Tick依赖说明](https://dev.epicgames.com/documentation/unreal-engine/actor-ticking-in-unreal-engine)，显式安排状态更新与动作完成的次序。
