## 2. 用户可感知的验收目标

本单必须让玩家观察到以下差异，而不是只增加内部模块。

**目标一：说的是目标，不是逐个按钮。**“收集六份木材放回仓库”形成一个任务；背包不足时分趟交付，玩家不必重复下单。

**目标二：补充信息不会丢掉原来的限制。**“只在我指定的安全点采木材”缺数量；玩家补“六份”后，地点限制仍在。地点无法解析时不执行简化后的无限制任务。

**目标三：记忆有来历、有时效、有撤销效果。**“我上次看到仓库有三份”和“你说有一百份”能够同时存在，但来源不同。撤销偏好后不再把它当成当前偏好，读回旧档则恢复旧档当时的有效记录。

**目标四：失败不装成功。**路被堵、资源耗尽、材料被别人用掉时，展示实际交付量及具体失败原因，不无限原地重试，也不自动绕过玩家限制。

**目标五：模型不可用时基本控制仍可用。**取消、规范任务卡确认、查看任务进度和显式记忆管理不依赖再完成一次模型推理。

**目标六：恢复旧档后没有“未来弟弟”。**旧回复、旧UI确认、旧导航和旧入库回调均不能改变新时间线。

B阶段另要求：在已批准的安全场景中完成一次真实制作和一次真实维修；必须看到实际扣料、产物/耐久变化和可回档状态。

## 3. 总体设计：生成式理解，确定性执行

```text
自由文本 / 已结构化的快捷操作
             │
             ▼
输入与会话入口：角色、距离、会话代次、操作来源
             │
             ▼
上下文构建：有效目标框架 + 可知观察 + 有效记忆 + 当前能力
             │
             ▼
单次本地4B：提出意图、缺失槽位、参数或文字回复
             │                         ┌──────────────────┐
             ▼                         │ 绝不由模型写入： │
严格解析 → 语义/权限/约束检查           │ 库存、血量、经验 │
             │                         │ 身份、世界真值   │
             ▼                         └──────────────────┘
UE编译规范任务卡 / 只读答复 / 澄清 / 不支持
             │
   必要的人类确认（不再次调用模型）
             │
             ▼
真实执行器：导航 → 动作 → 原子结算 → 实际回执
             │
             ├── 任务进度、UI状态、可知事件记忆
             └── 世界/任务/认知同边界快照与恢复
```

这些是逻辑职责，不要求实现成十个Subsystem，更不要求十个LLM。

优先复用 `UHearthwardLocalAISubsystem`、`FHearthwardNPCMemory`、`FHearthwardCompanionCommand`、既有库存/仓储结算和SaveSubsystem。先拆清测试边界，再按必要程度拆文件；不以架构升级为理由全仓重构。

底层动作可以继续使用现有状态机/导航/计时器。日后使用UE行为树也只是执行层选择，不把LLM放进每帧Tick来决定移动和攻击。Epic文档中的行为树采用事件驱动方向，可作执行层参考，但本单不强制迁移。[E4]

## 4. 单一能力目录与执行接口

### 4.1 能力目录是实际可做事情的唯一入口

每项能力至少记录：

| 字段 | 含义 |
|---|---|
| `capability_id / version` | 稳定标识与契约版本 |
| `availability` | enabled / temporarily_unavailable / not_implemented |
| `input_spec` | 合法物品、数量单位、对象引用和可选参数 |
| `allowed_contexts` | 安全独立、同行、营地等已落实环境，不由模型自报安全 |
| `supported_constraints` | 该能力真正能强制执行的约束类型 |
| `required_observations` | 生成候选前可以读取的角色可知数据 |
| `preconditions` | 接受和每次写入前必须满足的实际条件 |
| `effects / receipt_spec` | 实际变更及可验证回执，不是模型期望 |
| `cancel_policy` | 可中断点和已发生效果的保留方式 |
| `save_policy` | 可保存状态、恢复步骤与旧回调作废规则 |
| `work_budget` | 单次安全批量、无进展限制与最大底层重试次数 |

目录由工程已注册的执行器和受控配置组成。模型不能注册能力、修改版本或将`not_implemented`改成`enabled`。

同一份目录用于：构建提示中的能力说明、构建实际支持的Schema分支/枚举、校验解析结果、显示UI能力、生成测试覆盖清单。**物品存在于游戏目录，不代表弟弟已经能采集它。**

### 4.2 025能力范围

| 能力 | A：核心强化 | B：批准后扩展 |
|---|---|---|
| `inventory` | 按当前/上次亲见信息查询；维持UE生成数量答复 | 可扩展到批准的其他可知容器，不泄露远方最新数值 |
| `recall` | 查询现存有效记录，返回来源引用 | 查询已经落地的本人行动事件 |
| `collect` | 现有安全采集与真实交付，先以木材回归 | 经实际能力注册再开放其他物品/资源点 |
| `cancel` | 目标明确时直接取消当前实际任务 | 不改变其性质 |
| `clarify / dialogue / refuse` | 无世界写入 | 不改变其性质 |
| `rule_proposal` | 提出类型化规则卡，玩家确认前不生效 | 保持同一边界 |
| `craft` | 不显示为可执行；如实说明未接入 | 接通已有原型工作台配方与真实产物入库 |
| `repair` | 不显示为可执行；如实说明未接入 | 只维修明确归属、可唯一指认的授权装备 |
| 战斗、救助、完整狩猎/养殖等 | 不新增LLM执行入口 | 本025不承诺接完这些系统 |

### 4.3 每个执行器的标准生命周期

逻辑接口可实现为现有类的成员/适配器，以下不是要求复制一套公共结构：

```text
Describe → Preview → Validate → Start → ObserveProgress
                                  │
                                  ├── CommitAtomicEffect → EmitReceipt
                                  ├── CancelAtSafeBoundary
                                  └── Fail / Block / Return / HoldSafely
```

`Preview`只读；`Validate`不扣料；实际变化只在领域结算接口发生。
`Start`不等于成功；`Completed`必须能指向已提交的实际结果。

## 5. 有界目标框架与多轮澄清

### 5.1 一个目标，不是开放式计划树

保存一个结构化的待执行目标框架，至少包含：

- 原始输入轮次与原话引用；当前目标类型；明确物品/对象；数量及单位。
- 数量语义：本任务新增采集量、累计交付目标、制作批数等。不能仅保存一个无单位整数。
- 已解析地点/目的地、已确认约束、未解决的原话片段。
- 当前具体缺失槽位、上一轮问了什么、对应会话修订。
- 候选尚未执行的标志、可确认的规范任务摘要。

每名伙伴最多一个执行目标、一个待澄清/待确认目标、一个在途生成请求。普通闲聊不自动覆盖执行任务，也不从历史文字重新启动旧目标。

“一个目标、三步骤”约束玩家理解的任务链。某一步内部可使用固定的导航与重试逻辑；不能把任意十步计划藏进一个叫`DoEverything`的步骤来规避限制。

### 5.2 澄清规则

| 输入情况 | 处理 |
|---|---|
| “采些木材” | 只追问尚缺的数量，不反复问已明确的物品 |
| 上轮问数量，本轮“四份” | 仅补齐该目标的数量槽位；其他限制不变 |
| 上轮采集，本轮“今天景色不错” | 作为闲聊；旧候选不执行 |
| “不是木材，是石头” | 修改对应槽位并重验能力；石头未注册可采集则不执行 |
| “还是刚才那个数量” | 仅引用当前未结束目标中唯一明确的数量；否则澄清 |
| “再来六份” | 明确是新增六份还是把当前总量改成六份；不能猜 |
| “木材和矿石都收集，再造箭” | 指出超过本单支持的单目标边界，不偷偷只执行第一部分 |
| “先不要采；我只是在问” | 查询/讨论，没有任务副作用 |
| 新输入确实提交另一目标 | 先规范化并验证新目标，再按批准规则替换旧任务；失败候选不能吞掉旧任务 |

中文数字、数字字符串和目录别名可由规则辅助规范化，但“左右、随便、差不多、够用”等表达不能自动变成未经确认的精确数量。

保留当前1000字符单次输入、四轮/800字符澄清的原型限制作为初始兼容边界；同时增加真实token检查。达到容量时保留可见草稿并要求重述或编辑任务卡，不静默截断原始限制，不循环追问同一个已经回答的问题。

### 5.3 确认策略：用一次确认换取可控执行

**本版新增提案，须Owner批准：自由文本产生世界写入的任务先展示规范任务卡，再一次确认执行。**这不是每一步都弹确认。

- 卡片展示动作、对象、数量、地点、约束、目的地、可能消耗和替换的旧目标。
- 原话保留可查看；不能把“系统理解的卡片”伪装成玩家已经批准。
- 有任何未解决限制时，不提供可执行确认；明确列出未理解部分。
- 确认是绑定候选ID、修订和时间线的结构化UI操作，**不调用第二次LLM**。
- 已结构化快捷操作可直接经过相同校验；用户已经在该入口明确选择参数时，不再二次询问。
- 纯查询、闲聊、查看记忆不弹世界写入确认。
- “停止当前任务”快捷操作立即进入取消路径，不因模型忙而失效。

理由：单个模型没有办法证明自己完整理解了所有自然语言限制；只靠它输出`confidence=0.99`不能提供保障。任务卡让玩家核对最终被执行的明确契约。若保留简单口令自动执行，必须另有批准、范围白名单与独立误执行评测，不能把全量自由输入都默认为简单口令。

## 6. 类型化约束：从“记住”变成“执行时检查”

### 6.1 四种不同性质的信息

1. `claim`：玩家的陈述，未经核实，不改世界。
2. `preference / agreement`：交流参考，不能承诺任意文字都有强制执行器。
3. `typed_constraint`：玩家明确确认，且当前能力有对应校验器的规则。
4. 固定安全/权限规则：工程维护，玩家对话不能关闭。

旧 `collection_ban` 保留并迁移为等价的类型化“禁止采集指定物品”约束；不能迁移后失效。

### 6.2 第一批可以落实的约束

| 类型 | 示例 | 验证边界 |
|---|---|---|
| 禁止能力-物品组合 | 不采木材 | 保留原采集禁令；提交和相关执行检查不可绕过 |
| 限定已解析资源来源 | 只用这个安全采集点 | 目标必须绑定当前可知实体候选；不凭文本创造地点 |
| 限定投入材料种类 | 本次不要消耗草药 | 仅在已接入的消耗能力上启用；其他能力不得假装支持 |
| 累计消耗上限 | 本次最多用六份木材 | 依据同一目标真实回执累计，跨批次不能重新获得预算 |

数量目标本身已有`quantity`语义，不再用另一个独立字段制造互相矛盾的目标数。

未实现的限制，如“尽量别让我失望”“如果看起来划算就做”，只能作为偏好、请求澄清或不支持，不标记为“保证遵守”。不支持的物品标签、材料替代、任意条件表达式，也不能仅因模型写得像代码就执行。

### 6.3 规则来源、范围与冲突

每条类型化规则保存：稳定ID、版本、来源记录/原话、玩家确认事件、目标能力/对象、范围、有效状态和创建时间线。

- 当次限制默认绑定当前目标；“以后一直”形成待确认的长期规则卡。
- 未获确认的模型提案不能自动写入长期记忆或改变任务权限。
- 规则优先级：不可改的安全权限 → 当前目标绑定的强制规则 → 明确目标参数 → 交流偏好。
- 新旧规则矛盾时展示冲突对象，不让模型静默忽略其中一条。
- 当前025已经采用“新增/撤销记录不自动取消已接受任务”。本版默认保留：执行目标绑定接受时的规则版本；规则修改影响后续接受的目标。
- UI提供明确的“同时取消当前目标并重新安排”操作；用户选择后才打断原目标。若要让新规则立刻影响所有执行任务，须另作玩法批准。
- 安全条件、能力被禁用、时间线失效与对象销毁始终即时复核，不受上述玩家规则快照例外限制。

**消耗预算不是资源预留。**预算不锁定库存，其他生产仍可使用同一材料；轮到弟弟实际结算时材料不足，就失败/受阻，不伪造库存，也不阻止其他人合法使用物资。

## 7. 记忆：事实、经历、玩家话语分开存

### 7.1 数据层次

| 层次 | 写入者 | 用途 |
|---|---|---|
| 世界权威状态 | 现有游戏系统 | 库存、物体、任务、耐久；不由AI重复维护第二套真值 |
| 角色观察快照 | 可知性适配器 | 弟弟实际看到的地点/库存及观察时间，不全局同步 |
| 本人事件记忆 | 实际执行回执的确定性投影 | 真实采集、交付、受阻、取消等本人经历 |
| 玩家显式记录 | 玩家确认的UI操作 | 陈述、偏好、文字约定及类型化规则 |
| 工作记忆 | 会话管理器 | 原话、槽位、澄清、待确认候选；有界、可取消 |
| 派生索引与缓存 | 本地检索器 | 可重建，只是检索加速，不是事实来源 |
| 研发诊断日志 | 仅开发模式 | 排错与评测；永不重新作为角色记忆检索来源 |

**本版新增的自动事件记忆不等于模型自动总结。**只能由已经提交的本人行动回执生成固定结构记录。未经批准，不增加自动提炼玩家性格、自动写入长期约定或后台反思推理。

### 7.2 来源与可知性字段

记录至少具有：`record_id`、`record_revision`、`campaign_id`、记录类别、来源、主体/对象ID、事件或观察时刻、有效/撤销状态、原话或实际回执引用。

角色事件只来自本人参与、当前可见或明确告知的事件。远方族人的劳动、隐藏容器、未探索地点、未来任务及其他存档分支不能进入NPC检索候选。

营地信息继续复用当前 `IsAtCamp()` 的实际观察条件，避免另写一套互相矛盾的到营判断。**30米交流范围不等于30米内自动知道所有营地库存。**本单不擅自扩大亲见半径。[R3]、[R6]

### 7.3 时间与真实性

- 当前亲见数值 → 可作为“现在看到”的依据。
- 离营前的数值 → 只能表述“上次看到”；过期不是删除历史。
- 玩家陈述 → 可以引用“你之前告诉我”，不能升级为亲见。
- 现场观察推翻玩家陈述 → 世界不变；保留陈述来源，标记被后续观察纠正，不倒改原话。
- 没有可支持记录 → “没有找到相关记录”，而不是断言这件事在所有过去都没发生。
- 行动事件写入发生在结果提交之后；收到模型计划不能记录为“完成了一次采集”。

### 7.4 容量与撤销

建议初始工程上限：玩家活跃记录64条，活跃普通文字约定4条，本人事件记忆128条。它们是本任务的可调工程预算，不是最终玩法数值。

- 撤销记录不再永久占用活跃记录名额；不复用旧记录ID。
- 撤销、修改或压缩时提升记忆修订，废止引用旧修订的请求、候选、UI句柄和派生索引。
- 只在没有未完成快照/结算引用的安全边界压缩失效条目；必要时清空并从当前规范记录重建检索索引。
- 旧诊断日志与原始历史交流不作为恢复已删除记录的后备搜索源。
- 达到活跃上限时明确提示管理记录；不自动丢掉有效强制规则。
- 事件容量满时可按确定性方式合并重复的本人普通事件或淘汰旧的低价值事件；不删除在执行任务的必要结果账本。
- **事件记忆、执行去重账本、撤销索引不是同一份列表。**清理聊天记忆不能导致重复发放物品。
- 加载较早存档可以恢复当时还有效的记录，这是时间线恢复；不等同于当前存档中撤销失败。跨所有存档的隐私删除不属于本025默认功能。

## 8. 检索与上下文预算

### 8.1 先过滤，再排序

顺序必须是：

```text
当前campaign和已恢复快照
  → 有效记录 / 可知范围 / 未撤销 / 合法来源
  → 明确实体、物品ID与当前目标关联
  → 原话词项、目录别名和中文片段匹配
  → 去重、时效与相关性排序
  → 在token预算内组装上下文
```

不同证据等级分桶，不把来源权威性简单乘进一个总分后允许玩家陈述压过亲见事实。

### 8.2 不增加生成调用的改进

- 目录维护可审查的物品别名；中文数字规范化与指代只作用于当前明确目标。
- 明确物品、目标、地点引用优先精确匹配；原词项/片段检索保留为可解释后备。
- 待澄清目标中已经解析的实体也参与检索，避免只拿“四份”去找历史记忆。
- `recall`支持查到多条相关记录并让玩家选，不永远只把第一条返回成唯一记忆。
- 若同义表达没有任何命中，不用LLM编出一条“可能记得”的往事；可引导玩家选择记忆类别或查看清单。
- 不把检索结果自动写回长期记录，也不把模型此次措辞当作新事实。

工程可提供`IRetriever`等效边界以便日后对比Embedding；本单不部署新Embedding模型、向量服务或下载依赖。日后必须以留出集召回改善、CPU/显存成本和存档可重建性证明收益。

### 8.3 上下文的固定区与可裁剪区

**不可因低相关分被裁剪：**固定身份和权限、当前能力契约、当前原话中未解决的限制、当前目标规范槽位、执行所需的约束引用与版本。

**优先保留：**本轮直接相关观察和原话、相关结果回执、少量初始知识。

**先裁剪：**重复的修辞性历史、无关偏好、过期但本轮无关的事件。

所有适用强制规则始终由UE检查，不依赖它们是否完整出现在检索Top-K中。相关约束无法在上下文中清楚表达时，不执行受影响的自由文本提案，改为可编辑规范卡/澄清。

### 8.4 使用真实token边界

基线锁定为4096上下文、256输出tokens、并发1、temperature 0、thinking关闭。[R7]

候选输入预算：完整模板化请求最多3328 tokens，输出预留256，另保留512余量。计数包含系统信息、消息角色模板、Schema说明和全部发送内容；不能把“字符数小于800”当作token保证。

能否使用当前固定llama.cpp版本的token计数接口，应在实现时核验；不得假定master文档的所有能力都已经存在于固定构建。格式及token预算必须有最大输入边界测试。

若v2输出结构在256 tokens内无法可靠完成，先减少重复字段和台词，不静默增加第二轮推理。需要提高输出预算时，单独记录配置变更与性能对比；仍受4096总窗口限制。

## 9. 结构化输出与规范任务卡

### 9.1 模型能提供什么

保留原意图词汇的兼容映射：`collect / cancel / clarify / dialogue / refuse / inventory / recall`。新`craft / repair / rule_proposal`只有在相应版本和能力获准后启用。

模型输出的目标是一个**可被拒绝的提议**，不是直接的世界操作。数量、目标引用、规则、完整性都要复核。

建议按意图定义互斥的Schema分支，不要求所有意图都携带无意义的动作字段；`additionalProperties:false`。解析器独立检查字段、整数边界、数组上限和条件一致性，不只相信生成时的语法约束。

llama.cpp文档明确其JSON-Schema转换支持子集，某些不支持的特性可能被跳过；因此本单必须测试固定运行版本支持的语法，并保留完整的UE领域验证。[E3]

### 9.2 模型提议示例（候选格式，不是现有API）

```json
{
  "intent": "collect",
  "item": "wood",
  "quantity": 6,
  "quantity_mode": "additional_acquired",
  "source_ref": "S1",
  "constraint_refs": ["C1"],
  "unresolved": [],
  "npc_line": "我会按你指定的地方收集木材，再送回营地。"
}
```

`S1/C1`只能引用本轮上下文里由UE提供的候选映射。输出未知ID、无权对象、未注册物品、未支持数量语义、未解决原话片段，均不能进入执行。

`unresolved`为空只是模型的自报，**不是语义完整性的证明**；仍有规范卡确认和领域校验。模型不得生成真实operation_id、epoch、授权令牌或任意反射调用名称。

完整Schema、解析器和旧格式迁移测试是实现交付项；以上示例不替代它们。

### 9.3 UE持有的执行封套

复用/扩展原有 `FHearthwardCommandTicket` 的Id/Epoch/Revision，不平行复制第二套互相矛盾的命令身份。以下是需要覆盖的逻辑字段，不要求全部进入模型输出：

```text
campaign_id
runtime_epoch                 // 每次恢复/新世界生成，不能从旧档直接复用
conversation_generation
request_id / proposal_id
command_id / command_revision
capability_version
memory_revision / rule_revision
bound_rule_versions
read_set                      // 本任务实际依赖的对象及修订
approved_goal                 // 玩家确认后的规范目标
operation_id                  // 每个原子副作用独立稳定标识
payload_hash                  // 同ID重试须载荷一致
```

不要因为远处无关树木刷新就让所有命令失效；依赖检查针对本目标的对象/材料/规则。反之，目标实体销毁、材料改变、权限变化和候选版本过期必须重新检查。

### 9.4 防止“说的”与“做的”不一致

接受、完成、失败、数量、实际库存、旧观察和明确记忆引用，由UE使用规范数据/回执生成主要事实文本。

对会改变世界的意图，不直接展示未经核验的`npc_line`作为执行确认。可以保留少量无事实承诺的角色语气，但不能只靠禁词过滤判断“已经完成”是否被伪装表达。

闲聊允许自由表达；不能承诺完全杜绝所有无依据闲聊。涉及具体库存、任务结果和过去原话时转为受控答复。角色风格质量单独人工评价，不以模板覆盖一切来伪造高正确率。

## 10. 接受、执行、取消与失败恢复

### 10.1 状态边界

```text
输入 → 待澄清 → 提案就绪 → 待确认 → 已接受 → 执行中 → 完成
                                          │
                                          ├─ 受阻返营 → 营地等待
                                          ├─ 已取消 / 被替换
                                          └─ 回程也不可达 → 安全停留并保留真实物资
```

等待模型、等待玩家确认、世界暂停、路线受阻是不同状态；不要全部显示“思考中”。工程状态名可以细分，但对玩家只展示有用信息。

### 10.2 接受和每次副作用前复核

- 请求/候选/命令是否仍属于当前时间线和有效修订。
- 发出或确认时是否满足交流权限与30米距离；已接受的安全任务可以离开交流范围继续执行，不能把30米误作整个任务的活动半径。
- 目标/资源/设施是否存在且属于当前世界，实际路线与能力安全条件是否满足。
- 当前目标绑定规则、消耗预算、数量上限、材料、容量及其他领域前置条件。
- 是否处于恢复、原子结算、禁止执行的暂停/危险状态。

检查失败返回稳定错误码和可见原因，不仅是“不能做”；原始模型提议仍可保留在开发证据中。

### 10.3 多趟采集与完成判定

复用既有 `collect → return → deposit` 闭环。`requested/acquired/carried/delivered`分别表示目标数量、新采集量、当前携带和已经完成的归属交付。

- “再采六份”不能把接单之前背包里已有的两份当成新采集六份的一部分。
- 通过任务归属计数记录本任务产物，不要求此任务引入完整物品实例系统。
- 入库只累计本任务实际搬入的份数；旁人向共享仓库放入材料不增加弟弟的任务进度。
- 同一资源点允许按容量多趟；资源枯竭后不得悄悄换到未授权的新地点。
- 取消/替换时保留已经取得和已入库的真实物资；不删除产物，也不凭空把携带物转入仓库。
- 目标结束后，再次新下达相同文字是新任务，不被历史文本去重误杀。

### 10.4 原子副作用和重复请求

复用已有库存/仓储原子操作及operation_id去重，不另起一个不一致的库存系统。[R8]

每次可见原子变更至少绑定：`operation_id + payload_hash + runtime_epoch + command_revision`。同一ID、同一载荷的重试返回原结果，不再扣料/给物；同一ID但不同载荷明确拒绝。

扣料、产物/耐久变化、目标累计与结果事件必须在同一不可重入的逻辑提交边界完成；保存不得看到“库存已改、进度未改”的中间态。现有Transfer的重放返回`MovedCount=0`时，不能再次累计任务奖励或完成数量。

这里追求的是**当前时间线内每个已识别原子操作至多提交一次，并在未知结果时先核对账本**，不是对任意崩溃和外部系统宣称无法证明的“全局exactly-once”。

### 10.5 重试、卡住与安全停留

候选工程预算：同一底层导航失败最多重试2次；连续15实玩秒没有有效位移或进度，触发受阻检查。原地合法采集计时不算卡住。预算需在固定夹具中测试，可通过配置调整。

- 只对同一目标、同一语义、相同授权的可恢复瞬时错误重试。
- 不重试扣料以期待第二次“碰巧成功”；先查询原operation_id结果。
- 不调用LLM不断换计划，不增加自动反思循环。
- 回营路线也失败则原地安全停留，保存真实位置/背包和失败原因；不能瞬移或销毁物资。
- 存在新危险时先交给确定性安全执行层处理；基础安全感知未接通时，只在明确安全夹具里演示，不声称已验证开放世界安全。

### 10.6 三种取消分开

| 操作 | 效果 |
|---|---|
| 取消本次思考 | 废止在途推理与未接受提案；不自动取消已经执行的任务 |
| 结束当前澄清 | 清理该待澄清目标；不取消另一个已接受任务 |
| 停止执行任务 | 中断可停止动作，在原子提交边界之后保留已发生效果；废止后续命令动作 |

覆盖旧任务必须明确展示旧任务ID和已交付数量，避免“新提案还没校验，就丢掉正在做的事”。

## 11. B阶段：接入制作与维修，而不是只增加聊天意图

### 11.1 已确认的工程事实

已有 `HearthwardCrafting.cpp` 与 `HearthwardRepair.cpp`，但这些入口使用BuildingComponent的Owner、Owner的Gameplay/Inventory组件、已建工作台列表和可达条件。不能让弟弟直接调用玩家的Craft/Repair，然后宣称弟弟完成了工作。[R9]、[R10]

本阶段需要新增路径/契约批准。未批准或未实现时，能力目录保持`not_implemented`；A阶段仍可独立交付。

### 11.2 最小接入策略

优先抽取/适配既有领域操作，传入明确执行上下文：操作者、实际材料容器、工作台ID、配方/装备引用、数量/批数、操作ID、时间线和授权范围。

- 不通过交换Owner、临时盗用玩家组件或直接修改玩家数组来“复用”。
- 检查组件为空、Owner销毁、站点销毁与世界变更，失败无副作用。
- 玩家现有制作/维修操作必须维持原有验收结果；不能为NPC功能破坏玩家路径。
- 配方及费用只读现有数据，不新增正式经济数值；继续保留PROTOTYPE_ONLY标记。
- 通用配方知识与玩家库存访问权是两件事。模型知道配方，不代表有权从玩家背包扣料。

### 11.3 制作闭环

示例目标：使用明确授权的材料，在营地工作台制作若干批箭矢，并将产物交到共享仓库。

最多三个可解释宏步骤：`取得已授权材料 → 到站制作 → 产物入库`。其中导航是固定动作过程，不允许顺便新增采矿、交易或自主材料替代目标。

- 默认只使用弟弟背包已有材料，或任务卡明确允许从营地共享仓库提取的材料。
- 从仓库提取材料必须实际到达访问位置，通过已有转移语义；不能远程扣仓库。
- 要求成品件数，而配方按批生产时，展示实际批数、产量与余量；不能静默向上取整消耗更多资源。
- 无足够原料时报告，不自行添加采集子任务；玩家另行下单或明确批准后续扩展。
- 真正制作在达到站点且复核通过后发生；即时制作不等于任意地点隔空制作。
- 每批/整批失败语义与原制作系统一致，不把整批原子制作偷偷改为无提示的部分制作。
- 完成依据是实际产物交付与操作回执，不是模型声称“造好了”。

### 11.4 维修闭环

首轮只支持明确归属、可唯一识别的目标。默认维修弟弟自己携带且获授权的装备；“修我身上那把刀”涉及玩家装备转移/使用权，未接入时澄清或拒绝。

基线耐久按ItemId存储，并非已确认存在逐件装备GUID。实现Agent必须沿用真实数据模型；若同类多件装备无法唯一指认，不得伪造实例系统或随意维修其中一件。先拒绝歧义目标，逐件装备化留独立任务。

维修校验实际持有、耐久、费用、工作台、容量及权限；回执记录维修前后耐久和真实消耗。重复确认/重复回调不能重复扣料。满耐久时明确无需维修。

## 13. 请求生命周期、性能与降级

### 13.1 两套时钟

网络启动/推理超时、界面“仍在思考”提示使用真实单调时间；世界行动、观察时刻、饥饿和任务进度使用项目既有活动时间。

不能因为游戏暂停就让HTTP永久无超时，也不能为了等待模型让世界时钟偷偷前进。暂停中的异步结果可以暂存并失去执行资格，恢复时重新校验；是否允许在暂停界面发起推理，按R09局部批准与现有输入流程处理，不在本单暗自改全局暂停选项。

### 13.2 请求管理

- 一个活跃生成请求；一个可替换的未发送请求槽位，不建立无上限队列。
- 原有进程加载、回环地址、取消和请求序号保护必须回归。
- 相同UI发送事件去重；相同文字的另一条真实用户消息不能被永久去重。
- 网络取消是尽力而为；无论旧推理是否真的停止，其结果都必须经代次检查作废。
- 健康检查与生成请求生命周期分开管理，避免一个共享请求句柄相互覆盖；是否需拆字段由实际代码检查决定。
- 模型崩溃或不健康时，不擅自结束别的程序；只管理本游戏启动并持有的进程。

### 13.3 初始预算与体验门槛（目标，不是实测结果）

| 项目 | 候选目标/规则 |
|---|---|
| 生成式调用 | 每轮自由输入最多1次；错误后不隐式二次修复 |
| 在途生成 | 1；确认和取消等确定性UI不排队等模型 |
| 初始上下文/输出 | 维持4096/256；调整必须绑定配置和性能报告 |
| 暖机响应 | 在原测试同配置机器上争取P95 ≤ 8秒；不能拿别的硬件直接判达标 |
| 确认/取消UI反馈 | 本机目标100毫秒以内，记录实际结果，不阻塞主线程等待模型 |
| 原HTTP上限 | 初始沿用120秒；提供可见阶段、耗时和取消，不用无限等待掩盖死进程 |
| 自动生成重试 | 0；玩家可以显式重试，形成新的请求，不重放旧世界操作 |
| 执行器瞬时重试 | 同目标底层动作最多2次，不包含改目标、换材料 |
| 连续故障 | 候选3次触发暂时熔断，保留基础UI操作；恢复需健康检查或用户重试 |

原交接中的11.95秒首条、3.38秒中位等只属于当时特定机器与15条场景，不当成普遍保证。[R3]

CPU兼容路径必须实际测试并单独报告；记录CPU/RAM/GPU/VRAM、引擎及游戏画面负载、冷暖启动、输入输出tokens。除了推理耗时，还记录推理前后帧时间、显存峰值、UI响应。不能只在空场景跑模型，宣称游戏运行不会掉帧。

### 13.4 降级路径

格式无效、截断、模型未就绪、超时或能力不可用时：不执行候选；保留草稿；提供“修改任务卡/稍后再试/结束本次交流”。

确定性库存查看、显式记忆管理、停止任务和已规范化快捷命令可继续使用。其结果与日志必须标记为`deterministic_fallback`，不能计入真实模型理解成功率。

## 14. 存档、迁移和跨时间线一致性

### 14.1 快照内容

与现有CT-003协调保存：角色观察、有效玩家记录、规则与绑定版本、本人事件、工作记忆、已接受目标与实际进度、每个动作的提交状态、必要去重/事件投影位置。

保存的是规范数据及可重建索引依据，不是一个指向最新全局数据库的路径。命令/库存/耐久/事件需要同一逻辑快照边界。

### 14.2 恢复顺序

```text
关闭新的世界写入入口
 → 废止当前推理、提案、UI、导航和动作代次
 → 读取并验证完整快照/必要迁移
 → 恢复实体、容器、时间、实际任务与规则
 → 恢复角色可知观察和工作记忆
 → 从该快照重建派生索引
 → 创建新的runtime_epoch、重绑有效任务
 → 重新检查前置条件，再开放交互
```

- 已接受的长期执行任务可在重绑后恢复；未接受模型提案不因读档自动获得批准。
- 新runtime_epoch不能直接沿用存档里的旧运行epoch。
- 进程重启后不能把旧内存地址、Actor指针或旧回调作为有效对象；通过已存在的稳定ID映射恢复，映射失败明确受阻。
- 读旧档后的世界允许重新发生该分支之后的行为；旧异步回调绝不能参与这次行为。
- “语义记录恢复”与“实时推理会话恢复”不同：保存可恢复的原话/槽位，不恢复未完成HTTP流。

### 14.3 迁移要求

增加schema版本并写显式迁移测试。旧版本合法缺字段可按兼容约定初始化；新版本字段存在但损坏时不能用“缺字段兼容”静默清空。

旧`claim/preference/agreement/collection_ban`、撤销状态、旧观察与未完成澄清必须有映射。迁移不会将普通文字约定自动升级为强制规则，也不会将旧日志重新当成有效玩家记录。

保存中断、迁移失败、索引重建失败和对象缺失都需明确错误状态。遵守全局50点档池，不新增隐藏的第51个用户回档点；内部临时原子写文件不是新的可选存档。

## 15. 安全、来源隔离与诊断

### 15.1 硬权限边界

模型不能执行控制台命令、脚本、反射函数名、文件路径访问或任意HTTP调用；只能返回注册Schema内的候选。

玩家文本、记忆原话、任务描述和工具结果是数据，不是高权限提示。不要把它们拼进高权限指令区后依赖一句“请忽略恶意内容”。标明来源并使用低权限数据消息；检索文本不能修改角色身份与工具目录。即使分隔正确，仍必须依靠权限与动作校验，不宣称提示词防注入绝对可靠。[E5]

### 15.2 本地运行与数据

保持loopback-only、不自动下载、不上传玩家聊天、不引入云账户。外部研发资料仅用于开发，不成为NPC联网浏览能力。

不要记录本机API密钥、绝对用户路径和无关个人信息。开发评测用合成/同意提供的文本；真实玩家对话日志默认不开启远端上传。原始推理输出用于本地诊断时限制大小和保留期，不进入角色检索。

### 15.3 可观察轨迹

每次试验记录：代码SHA、模型/运行库/提示/Schema/检索/能力版本、设备配置、用例ID、输入来源、上下文引用ID、实际token数、原始提议、最终应用意图、确认、前置条件结果、操作回执、结束状态与耗时。

诊断只需简短`reason_code`与可验证依据，不要求导出模型隐藏思维链。错误码示例：

```text
OUT_OF_RANGE / STALE_REQUEST / STALE_CONFIRMATION
UNSUPPORTED_CAPABILITY / AMBIGUOUS_TARGET / UNRESOLVED_CONSTRAINT
POLICY_CONFLICT / INSUFFICIENT_MATERIAL / CAPACITY_EXCEEDED
SOURCE_DEPLETED / PATH_BLOCKED / RETURN_UNREACHABLE
DUPLICATE_REPLAY / OPERATION_PAYLOAD_MISMATCH
CONTEXT_OVERFLOW / OUTPUT_INVALID / MODEL_UNAVAILABLE
SAVE_MIGRATION_FAILED / SNAPSHOT_INCONSISTENT
```

## 18. 评测设计与量化门槛

### 18.1 三层评测，不能混算

**确定性原生/状态测试：**不调用模型，直接输入合法/非法候选与故障，检查权限、状态、库存、回执和存档。用于证明执行边界。

**真实模型集成：**固定实际4B与运行库，经玩家文本、检索、真实生成、校验、确认及执行全过程。用于评估真实理解和任务完成。

**真实UI操作：**键鼠输入、中文输入法、确认、取消、修改、滚动、关闭重开、读档后旧面板。注入结构化命令不是自然语言能力，直接调用函数不是物理键鼠验证。

Agent评测应区分对话轨迹与环境最终结果，而不只看它说“完成了没有”。本版沿用该方向，并增加留出表达和重复试验。[E2]

### 18.2 数据集与比较

- 原025的15个真实场景作为回归种子，保留原始失败轨迹。
- 另建120条多样表达，建议60条开发集、60条留出集；来源覆盖下节各类场景，不用120条“采几块木材”的近重复样本充数。
- 涵盖数字、否定、纠正、指代、闲聊插入、条件、未实现请求、错误事实与注入文本。
- 关键高风险场景至少重复3次，报告每次结果与同例连续成功情况；不能只取三次中最好一次。
- 原版与增强版在相同输入、世界fixture、模型文件、硬件与预算下对比。原版不支持的新制作能力单独列新能力覆盖，不伪算成原版失败。
- 留出集不能反复参与提示词调优；泄露给调优过程后转开发集，并补充新的留出表达。

### 18.3 初始验收门槛（待实测，不是现成PASS）

| 指标 | 门槛 |
|---|---|
| 越权世界写入、跨时间线写入、重复副作用、已撤销记忆复活 | 测试中0次；任一失败阻塞相应阶段发布 |
| 权威数量答复、直接原话引用 | 测试中100%可追溯到允许的观察/记录，不能编造 |
| 完整且受支持目标的真实成功率 | 留出集目标≥95%；必须发生正确实际效果，不能只返回卡片 |
| 含歧义/条件目标 | 澄清或明确不支持算安全；声称支持的样本，在补充后完整达成率目标≥90% |
| 未授权副作用负例 | 0次误执行；假设/否定/闲聊不能触发任务 |
| 正常支持任务的错误拒绝率 | 目标≤5%，防止“全部拒绝”取得虚假的安全高分 |
| 任务确认后的范围一致性 | 测试中100%按批准对象、数量、来源和约束执行 |
| 基线回归 | 原支持场景无未解释退步；增加确认步骤要按新批准预期评价 |
| 人物自然度 | 独立人工审查：不出世界观、不讲内部字段、不过度重复、不制造无依据记忆 |
| 性能 | 按第13节同机报告；CPU/Shipping未跑明确NOT_RUN，不用GPU PIE代替 |

“测试中0次”不是数学证明生产环境永不出错。对未覆盖表述、自由闲聊与硬件差异继续记录残余风险。

### 18.4 防止评测自欺

分别统计模型原始提议、最终规范意图、UE阻断、用户澄清/确认、实际结果、降级答复。若模型错误被护栏拦下，安全测试可通过，但该条理解成功率不能记PASS。

不要以精确台词匹配拒绝有效同义表达；关键判断基于允许意图集合、约束与实际状态。不要用模型自己的“我完成了”来评判模型，更不要求另一个付费云模型担当唯一评审。
